# Agent Notification Design

## Goal

Build a LAN-only notification receiver for a Windows machine. Agents running on a Mac mini can send `start` and `stop` events to the Windows receiver, and Windows shows a desktop toast when a task starts or finishes.

The first implementation focuses on the Windows server and Claude Code integration. Codex is intentionally out of MVP scope, but the event protocol and sender boundary must allow future agent integrations without changing the Windows server contract.

## Non-Goals

- No authentication in MVP.
- No public internet exposure.
- No Codex hook configuration in MVP.
- No OpenClaw hook configuration in MVP.
- No user-customized notification text in MVP.
- No Windows Service for the toast process, because desktop toast delivery is tied to the user session.

## System Overview

The system has three parts:

1. Windows server
   - Listens for HTTP notification requests.
   - Advertises itself with mDNS/DNS-SD.
   - Shows Windows toast notifications.
   - Hosts a browser settings page.

2. Discovery/configuration skill
   - Runs inside Claude Code and Codex-capable environments as a skill folder.
   - Discovers Windows servers by browsing mDNS/DNS-SD service type `_agent-notify._tcp.local.`.
   - Lets the user choose a discovered URL and events.
   - Configures Claude Code hooks for `start` and `stop`.
   - Keeps sender scripts generic so future agents can reuse them.

3. Hook sender script
   - Receives agent hook input on stdin or environment.
   - Normalizes it into the common notification payload.
   - Sends `POST /notify` to the configured Windows URL.

## Windows Server

The Windows server is distributed as a single executable plus scripts:

```text
agent-notify-server.exe
start.bat
restart.bat
install-startup.bat
uninstall-startup.bat
```

The process runs in the logged-in user's desktop session so toast notifications work reliably.

### Scripts

- `start.bat`: starts the server once.
- `restart.bat`: stops any existing server process for this app, then starts a fresh one.
- `install-startup.bat`: registers current-user startup, preferably via Windows Task Scheduler with logon trigger.
- `uninstall-startup.bat`: removes the startup entry.

### HTTP API

Default listen address:

```text
0.0.0.0:17891
```

Endpoints:

- `GET /health`
  - Returns server status and version.

- `GET /manifest`
  - Returns discovery metadata:

```json
{
  "name": "Agent Notify Server",
  "version": "0.1.0",
  "url": "http://localhost:17891",
  "serviceType": "_agent-notify._tcp.local.",
  "supportedEvents": ["start", "stop"],
  "supportedStyles": ["clean", "status-color", "agent-badge", "compact"]
}
```

- `POST /notify`
  - Accepts a normalized notification event.
  - Returns `204 No Content` on success.
  - Returns `400` for invalid payloads.

Payload:

```json
{
  "agent": "claude",
  "event": "stop",
  "project": "agent-notification",
  "cwd": "/Users/<username>/project/agent-notification",
  "message": "Agent task complete",
  "timestamp": "2026-04-28T14:32:00+08:00",
  "sourcePayload": {}
}
```

Validation:

- `event` must be `start` or `stop` for MVP.
- `agent` should be a short string such as `claude`, `codex`, or `openclaw`.
- Unknown fields are ignored.
- `sourcePayload` is retained only for logging/debugging if logging is enabled.

### mDNS/DNS-SD Discovery

Automatic discovery uses one protocol only:

```text
_agent-notify._tcp.local.
```

The Windows server advertises an mDNS/DNS-SD service instance for its HTTP server on port `17891`.

TXT records:

```json
{
  "version": "0.1.0",
  "events": "start,stop",
  "styles": "clean,status-color,agent-badge,compact",
  "path": "/notify",
  "settings": "/settings"
}
```

The skill browses `_agent-notify._tcp.local.` and lists every discovered server. If mDNS discovery fails, the only fallback is manual URL entry. There is no UDP broadcast fallback and no subnet scanning fallback.

## Notification Styles

The server supports style presets in MVP. The notification content is generated by the server and is not user-editable yet.

MVP presets:

- `clean`: plain, low-distraction notification.
- `status-color`: visual status color by event. `start` uses blue; `stop` uses green.
- `agent-badge`: shows an agent badge or initial, useful when more agent types are added.
- `compact`: shorter layout for high-frequency notifications.

The stored config uses an extensible model:

```json
{
  "notificationStyle": "clean",
  "enabledEvents": ["start", "stop"],
  "futureOverrides": {}
}
```

`futureOverrides` is reserved for later customization such as title/body templates, sound, icon, urgency, per-agent rules, per-project rules, and event-specific styles. MVP should not expose those fields in the UI.

## Web Settings UI

The Windows server hosts a local settings page:

```text
http://<windows-ip>:17891/settings
```

MVP settings page:

- Shows server status.
- Shows HTTP URL and mDNS service type.
- Shows four notification style preset cards.
- Shows browser preview for each style.
- Saves the selected style.
- Enables/disables `start` and `stop` notifications.
- Provides `Send Test Toast`.
- Provides `Restart Server` guidance or button if safe to implement.

The UI should be simple and operational, not a marketing page. It is a local admin surface for a LAN utility.

Future customization can extend the same page with an advanced section, but MVP should keep only presets and event toggles visible.

## Skill Design

Skill directory:

```text
skills/agent-notify-discovery/
  SKILL.md
  scripts/discover.py
  scripts/send.py
  scripts/configure_claude.py
  references/hook-formats.md
```

### Skill Behavior

The skill should be used when the user asks to discover the Windows notification server, configure agent notifications, or update notification hook URLs/events.

Workflow:

1. Run `discover.py`.
2. Present discovered servers.
3. If none found, ask for manual URL.
4. Query `/manifest`.
5. Ask/select enabled events: `start`, `stop`, or both.
6. Configure Claude Code hooks.
7. Send a test notification.

### Sender Script

`send.py` is the stable integration boundary for all agents:

```bash
python scripts/send.py \
  --url http://localhost:17891 \
  --agent claude \
  --event stop
```

The script may also read JSON from stdin when run as a hook. It should never fail the agent task if the Windows server is unreachable; it logs the failure and exits successfully by default. This prevents notification problems from breaking agent workflows.

## Claude Code Hook Mapping

MVP configures Claude Code only.

- `start` maps to `SessionStart`.
- `stop` maps to `Stop`.

Claude Code command hooks pass JSON on stdin to `send.py`.

Generated hook commands should include:

- configured Windows URL
- agent name `claude`
- event name
- project/cwd extraction where possible

The skill should prefer project-local configuration when the user asks for a project-specific setup, and user-level configuration when the user asks for global setup.

## Future Agent Integration

Codex and OpenClaw are future integrations. The design reserves:

- generic payload fields: `agent`, `event`, `sourcePayload`
- generic sender script
- `references/hook-formats.md` for per-agent hook configuration notes
- server-side event validation that can expand beyond `start` and `stop`

Adding a new agent later should require:

1. Add an adapter/configure script for that agent.
2. Map native hook events to normalized events.
3. Reuse `send.py`.
4. Keep Windows server unchanged unless new event types or style capabilities are needed.

## Error Handling

Windows server:

- Invalid JSON returns `400`.
- Unsupported events return `400`.
- Toast delivery failure returns `500` and logs the error.
- `/health` remains available even if toast delivery fails.

Sender script:

- Timeout quickly.
- Print concise diagnostics.
- Exit `0` by default to avoid disrupting agent hooks.
- Optional strict mode can exit non-zero for manual tests.

Discovery:

- Browse `_agent-notify._tcp.local.` with mDNS/DNS-SD.
- Present every discovered server.
- `--manual <URL>` validates a provided URL with `/manifest`.
- No UDP broadcast.
- No subnet scanning.

## Security Notes

MVP has no authentication by user request. This means any device on the LAN that can reach the server can trigger notifications.

Mitigations:

- Bind only to LAN by default, not public interfaces when avoidable.
- Document firewall expectations.
- Keep `/notify` limited to notification events only.
- Do not expose shell execution through HTTP.
- Do not accept arbitrary notification templates from remote POST payloads.

Authentication can be added later with a shared token without changing the basic discovery or payload model.

## Codex Review Findings (Implementation Phase)

### Bugs to Fix

1. **Discovery protocol mismatch** - Existing UDP broadcast approach failed in Claude Code/macOS and should be replaced with mDNS/DNS-SD advertisement plus mDNS browsing. Manual URL is the only fallback.

2. **Manifest incomplete** - `handlers.go:18` `ManifestResponse` missing `url`, `supportedEvents`, `supportedStyles`. `configure_claude.py` needs these fields.

3. **Settings save bug** - Allowlist logic inverted in `settings.go:183`. UI builds empty `saveData`, style/events likely never persist.

### Install Script (Missing)

Add `scripts/install-skill.sh`:
- Detects repo root, validates skill files
- Creates `~/.claude/skills/`, copies or symlinks `skills/agent-notify-discovery`
- Idempotent, prints installed path
- Optionally runs discovery test

### Unit Tests (Expanded)

- mDNS/DNS-SD service type and TXT record formatting
- `POST /notify` invalid event returns `400`

**Go config/settings:**
